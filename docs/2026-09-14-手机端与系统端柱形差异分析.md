# 手机端 vs 系统端 FU2611 分时柱形差异 — 排查报告

日期：2026-09-14
标的：燃油 2611（FU2611）
对比对象：手机端行情 App 分时截图 vs 本系统前端分时副图

---

## 一、结论速览

| 项目 | 手机端 App | 本系统（校正前） | 本系统（校正后） |
|---|---|---|---|
| 09:00 首根量 | 与相邻分钟同量级，约 2 万级 | **162,352**（顶满副图） | **23,703** |
| 首根相对高度 | ≈ 与夜盘峰值持平 | ≈ 100%（其余压到 15%） | ≈ 99%（与夜盘峰值持平） |
| 价格线 OHLC | 一致 | 一致 | 一致 |
| OI 线范围 | 218,743 ~ 233,187 | 218,754 ~ 233,187 | 同左 |
| x 轴时段几何 | 夜盘约 33% 宽度 | 夜盘 34.7%（121/349 槽） | 同左 |

**核心结论：两端的价格线与 OI 线数据完全一致，唯一差异在「成交量柱」的取数口径。**
手机端 App **未采用**新浪分钟接口里 09:01 那条 `v=162352` 的异常值（或对其做了异常裁剪），
而本系统的历史回补链路曾**忠实镜像**了源端的这条脏值，导致 09:00 首根顶满副图。

该异常已于同日修复（见 `backend/storage/history_backfill.py` 的 `_sanitize_auction_in_candidates`），
校正后系统端与手机端观感**已趋于一致**。

## 二、涉及的接口与字段口径

### 2.1 新浪分钟线接口（两侧分时图的共同数据源）

```
GET https://stock2.finance.sina.com.cn/futures/api/jsonp.php/var _data=/InnerFuturesNewService.getFewMinLine?symbol=FU2611&type=1
```

| 字段 | 含义 | 备注 |
|---|---|---|
| `d` | **分钟结束时刻** | 如 `2026-09-14 09:01:00` 代表 09:00~09:01 这一分钟 |
| `o/h/l/c` | 该分钟开高低收 | |
| `v` | 该分钟成交量（手） | **争议字段** |
| `p` | 该分钟**持仓量** OI | 对应副图 OI 线 |

**关键口径**：`d` 是「分钟结束」标记。`type=1` 为 1 分钟，另有 5/15/30/60。

### 2.2 新浪实时报价接口（手机 App 顶栏数字来源）

```
GET https://hq.sinajs.cn/list=nf_FU2611
```

实测返回（2026-09-14）：
```
燃料油2611, 150000, 4230.000, 4523.000, 4203.000, 4392.000, 4392.000, 4394.000, 4392.000,
4365.000, 4292.000, 3, 8, 219380.000, 1263929, 沪, 燃料油, 2026-09-14, ...
                                  ↑持仓         ↑当日累计成交
```

- `219380` → 手机顶栏「持仓 219380」
- `1263929` → 当日累计成交量
- `4392` → 最新价（与手机大字 4392 吻合）

> 手机顶栏的 `VOLUME: 5851` / `OI: 219380` 属于**实时报价快照**字段，
> **不是**分时图光标处的分钟量。已在 1m 源中反查确认 `5851` 不存在于任何分钟，
> 也非相邻 2 根或 5 根之和 —— 它来自另一个实时推送，与柱形图无关。

## 三、两侧数据一致性核对（逐字段）

| 系统端 `market_bar.open_interest` | 218,754 ~ 233,187 |

→ **三者吻合**，证明两端用的是**同一条分钟序列**。

### 3.2 价格线：一致

手机主图分时线在 09:00 处出现跳空上冲（夜盘收 4292 → 日盘开 4430，最高 4523），
系统端 1m 数据首根 `O=4430`、日高 `4523`，形态与数值均吻合。

### 3.3 x 轴几何：一致

| 来源 | 夜盘占宽 |
|---|---|
| 手机截图目测 | ≈ 33~40% |
| 系统端 `intradaySessions()` 槽位 | 121 / (121+228) = **34.7%** |

→ 两端的交易时段槽位模型一致，排除「轴错位」。

### 3.4 成交量柱：**唯一差异点**

| 时刻 | 新浪源 `v` | 手机端柱高观感 | 系统端（校正前） |
|---|---|---|---|
| 2026-09-11 21:01 | 23,948 | 最高量级之一 | 23,948 |
| 2026-09-14 09:01 | **162,352** | **与 21:01 同量级（未顶满）** | **162,352 → 顶满** |

**量化差异**：

- 手机实测：09:01 与 21:01（23,948）**同量级**
- 系统校正后：09:00 = 23,703，相对夜盘峰 23,948 = **99.0%** → 与手机观感一致

## 四、差异根因

### 4.1 直接原因：源端 09:01 首次出现异常放大

新浪分钟源在 **2026-09-14** 把开盘集合竞价的累计委托量写入了日盘首根：

| 交易日 | 09:00 首根量 | 当日次高 | 倍数 |
|---|---|---|---|
| 2026-09-10 | 11,545 | 8,537 | 1.4x |
| 2026-09-11 | 27,639 | 18,126 | 1.5x |
| **2026-09-14** | **162,352** | **15,802** | **10.3x** |

正常日稳定在 1.4~1.5x，9/14 突然放大到 10.3x —— 属**源端异常写入**。

（注：日盘合计 807,026 与库内完全一致，说明**总量没坏，坏的是量在分钟间的分配比例**。）

### 4.2 传导原因：本系统「忠实镜像源」

`repair_minute_gaps` 的设计目标是「以历史源为准修正已收盘 K 线」，
因此会把源端的 162,352 原样灌入 `market_bar`，
前端 `renderSubChart()` 直接 `src.map(b => b.volume || 0)` 取 DB 值作图 → 首根顶满副图。

**前端无聚合、无换算错误**，问题 100% 在数据口径。

### 4.3 手机端为何正常

手机 App 未复现该异常。可能原因（按可能性排序）：

1. **App 端对分钟量做了异常裁剪/分位数截断**（较常见，避免个别脏值压扁整图）；
2. App 使用了另外的成交量聚合口径（如按 tick 重算），未直接采用该 `v` 字段；
3. App 的分钟线缓存早于异常发生时刻写入，未刷新该根。

无论哪种，**手机端的表现才是「正确观感」**，本系统原先的表现才是异常的。

## 五、修复与验证

修复实现位于 `backend/storage/history_backfill.py`：

- `_sanitize_auction_in_candidates()` —— 在 `repair_minute_gaps` **写库前**净化候选集
  - 基准 = 该合约历史正常日「首根/次高」倍数的中位数（剔除异常日）
  - 判定阈值：`min(max(3.0, k×3.0), max(3.0, k+1.5))`，溢出量 ≥ 1000 手
  - 校正：首根 = 次高 × k，差额按后续分钟量占比加权摊回，**日盘合计严格守恒**

### 验证结果

| 项目 | 结果 |
|---|---|
| 校正后 09:00 | 23,703（原 162,352） |
| 校正后倍数 | 1.5x（原 10.3x） |
| 日盘合计 | 807,026（**分毫未变**） |
| 全库扫描 | 13 处异常全部校正，`auction_fixed=0`（已收敛） |
| 与手机端观感 | 一致（首根与夜盘峰同量级） |
| 测试 | 178 项全部通过 |

## 六、遗留与建议

1. **前端可加防御**：`renderSubChart()` 对成交量做「分位数截断」或「异常倍数额定」，
   避免未来源端再吐脏值时整图被压扁（当前依赖后端净化，前端无兜底）。
2. **高阶周期口径**：5m/15m/30m/60m/1d 由本地引擎从 tick 合成，不含集合竞价，
   与 1m（含竞价）口径不一致 —— 待统一。
3. **手机端 `VOLUME: 5851` 字段来源**：属实时推送，与分钟柱无关，无需对齐。
