# 未来趋势预测问题解决方案

日期：2026-10-06。状态：已按第1至第5阶段实施代码改进，266项离线回归通过；LH/JD具体日期已取官方API证据，第二阶段已保存9份新浪行情原响应，服务已重启并完成只读API验收；官方证据补齐、真实模型内容和持续采集验收仍未完成。详见[开发验收](2026-10-06-未来趋势预测问题解决-开发验收.md)。

## 1. 目标与依据

先保证目标日期、行情口径和证据推理可靠，再提高有效预测覆盖率。不能通过放宽规则，让所有品种强行给出方向。

依据本轮真实运行：8合约、2模型，共16任务；14个任务产生并复核结果，其中11个不判断、3个偏空；AP两个任务连接失败。结果已入库并经API读回。详见 [实跑验收](evidence/2026-10-06-future-trend/delivery.md) 和 [问题记录](evidence/2026-10-06-future-trend/findings.md)。

本轮使用既有缓存，没有刷新全量资料。行情基准为9月30日，10月6日国庆休市；休市没有新国内行情不算故障。3/5交易日目标为10月12日/14日。当前只能评价流程与内容质量，不能评价尚未发生的预测准确率。

方案沿用现有后端、冻结快照、研究配置和结果接口。不开新系统，不修改冻结的CTP模块，不改变实盘交易设置。郑商所采集入口由用户继续研究，不列为本轮开发的完成前提。

## 2. 第一阶段：合约期限与统一判断门槛

### 问题

期限规则当前只覆盖FU，其余7合约是UNKNOWN，表示系统未核实。SA相同UNKNOWN输入，两个模型执行规则不同，说明提示词不能替代代码门槛。

### 处理

1. 核对BU、SC、SA、AP、LH、IH、JD的交易所官方合约规则，记录原文、来源、核验日期、适用时间和日历覆盖年份。优先覆盖当前8合约，不泛化全部品种。
2. 使用标准规则推导最后交易日，并保留“规则推导”与“合约专项调整公告核验”的区别。发现专项公告时以公告为准；不能由模型猜测期限。
3. 缺规则、缺适用年份日历、规则冲突或需要核对的调整公告未确认，均保留未知及具体原因。年份超出已核验日历时不套用旧年份假期。
4. 按3日、5日分别预检：目标日在期限内才进入方向判断；超过期限或无法确认，统一输出该期限NO_JUDGMENT。一个期限受阻，不连带阻断另一有效期限。
5. 两个期限都受阻时不调用模型，记录为规则阻断；一个受阻时允许模型分析有效期限，并在结果校验层禁止受阻期限出现方向、价格区间等正式预测。分析与复核使用同一门槛。

最小修改入口：`backend/ai_analysis/future_trend.py`的`contract_lifecycle`、`validate_result`，`snapshot.py`的快照冻结，`orchestrator.py`的调用前置校验。官方规则资料随实现保存，不在方案中编造未核对的最后交易日。

兼容现有状态：保留既有任务状态和NO_JUDGMENT结构，增加可读的原因及是否调用模型标识；统计分别列“模型完成”“规则阻断”“数据阻断”“调用失败”，不把零调用的不判断算作模型预测成功。如须增加持久化字段，先核对现有JSON结果容器，能复用就不新增表。

### 验收

- 当前8合约均取得有来源的规则结果，或明确列出外部核验阻塞项；UNKNOWN不得冒充已核实。
- 测试覆盖月底、假期、跨年、目标日等于最后交易日、3日有效而5日无效、日历年份未知及专项公告覆盖。
- 相同冻结输入下，两模型在“是否允许该期限给方向”上完全一致；双期限阻断时模型调用次数为0。

## 3. 第二阶段：行情核对与质量控制

### 问题

BU同日15分钟最高5204、日线最高5175；FU分钟最低4329、日线最低4355。它们是跨周期差异候选，尚不能直接认定哪些行错误。JD的60分钟序列从9月15日跳至9月30日，另有零成交量但持仓变化1052，现有条数检查不足。

### 处理

1. 先离线核对本轮数据：原始来源、具体合约、时间戳代表开端还是结束、夜盘归属、日线覆盖范围和入库过程。只检查非CTP历史行情链路；不得直接覆盖数据库。
2. 同一合约、同一交易日且确认可比覆盖范围后，比较分钟高低与日线范围。容差采用该品种已核验最小变动价位；超一跳列为差异候选。覆盖未知时显示“口径未核实”，不显示检查通过。
3. 按品种交易时段和交易日历建立预期已闭合柱，识别实际缺口。午休、夜盘停开、周末、假期和正在形成的柱不算缺失；不同来源的柱边界先归一再比较。
4. 保留相邻已提供柱的持仓差事实，但跨缺口时标明比较跨度，不能称为正常单周期变化。没有连续前柱时，供单周期推理使用的持仓差置空。
5. 零成交但持仓变化先列警告并禁用该柱量仓推断，核对后再确定来源异常。禁止拿覆盖不完整的历史周期量与报价累计量直接相减判错。
6. 质量分为警告与阻断，并冻结检查依据和受限用途：单个差异候选只警告，禁止用争议数据给精确支撑压力；非法OHLC、合约或交易日错配影响最近判断窗口时阻断。最新60m/15m预期连续窗口分别不足既有10/20根时阻断；日线沿用20根门槛。明确标注覆盖不完整的来源若不能满足这些要求，应补数据或不判断，不能靠总条数放行。
7. 经来源证实的错误，先备份受影响行，再做限定合约/日期的修复或回补，保留修复记录。证实不了则隔离推理用途，不猜算新值。

修改入口：`snapshot.py`的`build_future_snapshot`及现有非CTP历史入库入口；`orchestrator.py`、`future_trend.py`消费冻结的质量限制。先定位真实入库链路，再决定是否需要修改采集代码。

### 验收

- 本轮BU、FU差异和JD缺口都有可追溯核对结论，不能只增加一个警告字符串。
- 本地样例覆盖夜盘归属、午休、假期、时间标签、跨缺口持仓差、零量持仓变化及最近窗口不足。
- 一般警告不使全品种一律不判断；阻断数据不能通过模型复核重新放行。
- 修复后同一冻结输入可重复得到相同质量状态，正常休市数据不被误判为失联。

## 4. 第三阶段：加强语义复核

### 处理

复核除了核对引文与数字，还要逐条检查关键论断是否由证据支持：

| 检查项 | 可接受表述 | 必须拦截或修正 |
| --- | --- | --- |
| 持仓身份 | 总持仓下降，具体多空身份无法确认 | 仅凭总减仓断言多头获利了结、踩踏 |
| 事件状态 | 正在讨论、已宣布计划、已实施分别表达 | 计划释储直接计入已实现供应 |
| 统计口径 | 明确地区、指标、单位、数据期 | 国外进口替代中国进口、邻句期别移用 |
| 推理限制 | 区分确定事实、条件情景及缺口 | 受限行情仍作为精确价位或量能依据 |

在现有复核请求中加入关键论断清单、证据ID及支持关系，要求复核报告指出具体不支持的句子。代码确定性核验字段、引用、事件状态与门槛；涉及自然语言蕴含的判断由复核检查，不能声称关键词匹配就证明语义正确。

发现不支持论断时，最多修正一次并重新校验，纳入总调用预算；仍失败则保留草稿供查看，正式结果标为未通过复核。数据/期限硬阻断不能通过修正文案绕开。

入口：`orchestrator.py`分析与复核提示、现有复核失败分支，`future_trend.py`结果校验。尽量复用已有复核机制。

验收：以本轮FU论断和释储原文构造离线反例；复核通过必须展示关键论断的依据或修正记录。真实小样本复核人工检查仍可能漏判，报告不得将“复核通过”描述成推理绝对可靠。

## 5. 第四阶段：直接关联行情与基本面补缺

### 直接关联行情

复用已有研究设置，为8品种逐项确认直接关联候选及用途。FU/BU可先核对SC等能源参考，但必须验证具体月份合约有数据、仍有效及适用关系；IH可核对相关股指参考。其他品种根据产业链依据确定，不在代码中自动猜主力。

只采配置的直接关联，不递归扩展。每项记录合约、来源、时间、单位、参考用途和限制；未配置、已配置但无行情、已有有效行情三种状态分开。没有可靠关联时允许空配置并说明原因，不能为填满字段硬配。

### 基本面

| 品种 | 优先补项 | 有效性要求 |
| --- | --- | --- |
| FU | 中国进口/国内供应、船燃销售或加注需求 | 地区、指标、单位、统计期可核验；富查伊拉数据仅作该地区参考 |
| BU | 炼厂开工/产量统计期、道路施工量化需求 | 23.4%与38.2万吨需追回同源原报告；库存期别不能移用 |

指标覆盖区分“无资料”“有数值但期别未知”“口径不适用”“过期”“有效”。维度有资料不等于该维度关键指标齐全。保留原始引文，发布日期、数据期、核验时间各自记录；不能编造日期。官方仓单只反映其统计范围，不替代总库存、炼厂产量或终端需求。

入口：`web_research.py`的指标要求和期别检查、`research_cache.py`冻结覆盖、`research_scheduler.py`补缺，以及现有研究设置与关联快照。优先在已有字段中补状态；更详细状态对旧消费者保留兼容映射。

验收：有效关联实际进入冻结输入并可读回；无法取得数据的项显示具体原因。FU/BU每个关键指标按口径单独验收；登录或返回200不是正文与指标有效性通过。页面显示由用户验收，不自动打开浏览器。

## 6. 第五阶段：连接失败、输入负担与持续验收

### AP连接失败

两个首轮请求约16.7秒被断开，目前没有HTTP状态，不能确定是网关、服务端还是请求体原因。先按时间、模型、请求ID关联本地与可取得的上游日志；日志仅保存长度、耗时、状态和错误分类，不记录凭据。

默认最多重试1次，仅用于确定未得到有效响应的连接故障、429及可重试5xx。遵循Retry-After；没有该头时指数退避。重试共享原任务总截止时间，不给每次请求重新分配完整预算。400、鉴权/配置错误和解析校验失败不进行网络盲重试。

读取途中断开、服务端可能已生成的情况记录“结果未知”，优先查询供应商任务状态；不支持查询/幂等时不自动重发该类请求，避免重复付费。结果落库使用现有任务标识保持幂等，一个模型/合约失败不能阻断其他任务。

### 输入压缩

本轮30次调用，供应方报告输入token总计1816154。先去除重复元数据、重复文章并采用可还原的紧凑K线表示，保留精确数值、时间、证据ID、必要原文和多周期结构。复核保留判断所需完整证据；供应商缓存可另测，不假定已经生效。不先大幅截断行情或仅传模型生成摘要。

第一版验收目标：同冻结输入请求字符量中位数减少至少20%，没有证据ID、关键原文与必需行情丢失；否则保留原方案并报告未达标。模型token、延迟和实际费用分别报告，不把两家token计数当统一账单。

入口：`provider.py`网络调用与日志、`orchestrator.py`请求预算和`_model_snapshot`。不更换模型或放松业务门槛来改善成功率。

### 来源与多轮运行

本轮URL去重后东财占56.94%，仅说明这个切片；历史整体及持续验收未完成。至少观察3轮正常计划采集，跨2个实际交易日，不为验收高频访问官网。逐轮报告URL去重占比、转载内容聚类后的来源分布、各品种有效指标覆盖、采集失败率。

沿用东财占比低于60%的验收目标，同时报告同源转载集中度；不能删有效东财资料来制造达标，不能把新增域名或转载当新增独立证据。若三轮未达标，保留未完成状态并列具体缺失来源和指标。

## 7. 实施顺序与验证

| 顺序 | 交付 | 进入下一步的条件 |
| --- | --- | --- |
| 1 | 官方期限依据、逐期限代码门槛、原因统计 | 离线边界测试通过，UNKNOWN不能给正式方向 |
| 2 | 本轮行情核对记录、质量分级、必要修复 | 缺口/时段测试通过，修复行可回溯 |
| 3 | 关键论断复核与失败处理 | FU身份推断、事件状态反例被拦截 |
| 4 | 关联设置、基本面逐指标状态与补缺 | 有效/未知/缺失可区分，输入与结果可读回 |
| 5 | 有限重试、压缩对照、多轮验收报告 | 故障隔离与幂等通过，保留真实外部未完成项 |

优先扩展现有`test_future_trend`、`test_future_trend_integration`、`test_ai_analysis`、`test_ai_reliability`、`test_research_credibility`和`test_web_research`等测试，开发期使用冻结证据、本地fixture及模拟模型响应，避免每次改动付费实跑或访问交易所。

按当前项目环境使用unittest，示例（每个受影响测试文件分别执行）：

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -p "test_future_trend*.py"
.venv\Scripts\python.exe -m unittest discover -s tests -p "test_ai_reliability.py"
.venv\Scripts\python.exe -m unittest discover -s tests -p "test_research_credibility.py"
.venv\Scripts\python.exe -m unittest discover -s tests -p "test_web_research.py"
```

故障验收模拟断网、超时、429、5xx、响应中途断开及一个通道失败；检查次数、总预算、日志、任务终态和重复写入。受影响的API测试同时运行，不能仅测解析函数。

后端修改后按项目约定执行stop.bat、start.bat，确认8000监听及未登录auth/me返回401 JSON。纯文档修改不需重启。数据库修复先备份限定行，代码与配置保留修改前版本；回滚后重复健康和结果读回检查，不删除历史预测。

最终真实验收先限FU、BU、SA、AP四合约、两模型、单次分析与复核，覆盖方向、基本面缺口、规则一致性和连接问题：正常最多16次调用，另设最多4次全批补救调用及不超过上轮全量输入token的预算上限，先验证任务终态、规则和内容质量。通过后才扩到8合约，完整记录新增付费调用。预算采用供应方返回用量累计，未知用量列出估算误差，不能宣称费用已精确控制。

## 8. 完成定义与外部依赖

开发完成要求：代码门槛一致、离线测试通过、服务重启健康、冻结输入及最新结果API读回一致、故障隔离有效、明确显示未核验项。页面验收由用户完成。

官方期限公告、历史源覆盖说明、AP上游日志、付费正文权限和缺失基本面原报告属于外部证据依赖。拿不到时能完成状态表达与阻断，但相关数据验收仍未完成，不得写成已解决。

预测效果另做事后评估：到期后沿用冻结的参考价和目标日收盘口径，分别统计3日/5日方向、区间命中、覆盖率及不判断比例；关联到当时冻结输入，不事后换合约或补资料。至少积累20个不同预测起点，并披露重叠窗口和样本相关性；该门槛只是开始评价的条件，不代表证明稳定盈利。证据完整度评分始终不叫胜率。

本方案已实施业务代码改进并完成离线测试、服务重启和既有结果API读回；本次开发未新增付费模型调用，未修生产行情数据。阶段性成果和剩余外部依赖以[开发验收](2026-10-06-未来趋势预测问题解决-开发验收.md)为准。
