# 2026-09-14 安全加固与遗留清理

## 背景

对系统做了一次完整的代码审查（后端 53 个 Python 文件、测试套件、配置、前端），发现若干安全与工程卫生问题。本次修复其中无需外部依赖的部分。

## 修复内容

### 1. 敏感凭据外置（不再明文入 YAML）

**问题**：`config/settings.yaml` 内含 CTP 密码、MySQL 密码明文；`docker-compose.yml` 中 MySQL root 密码硬编码两处（含 healthcheck）。

**改动**：
- 新增 `.env` 存放全部敏感值，`backend/common/config.py` 新增极简 `load_dotenv()`（无新增依赖），在 `load_config()` 最早阶段加载。
- 新增 `_ENV_OVERRIDES` 映射表 + `apply_env_overrides()`：环境变量优先级高于 YAML，可覆盖 ctp/mysql/redis/system 各类字段。
- `settings.yaml` 中所有密码字段清空并注明对应环境变量名。
- `docker-compose.yml` 改用 `env_file: .env`，MySQL 密码引用 `${FUTURES_MYSQL_PASSWORD:?...}`（未配置时 compose 直接报错，不再静默使用弱密码）。
- 新增 `.gitignore` / `.dockerignore`，`.env`、`session_secret.key`、`users.yaml`、`ctp_flow/` 等均已忽略。

**兼容性**：`.env` 中已填入原有值，行为与改动前完全一致，无需改代码即可继续运行。

### 2. 维护接口 fail-closed + 恒定时间比较

**问题**：`maintenance_token` 默认值为硬编码弱令牌 `citic_futures_admin_2026`，且 `settings.yaml` 未覆盖它——即维护接口实际以公开默认值运行。

**改动**：
- `SystemConfig.maintenance_token` 默认值改为空字符串。
- 新增 `verify_admin_token()`（`routes.py`）：令牌未配置时返回 **503**（而非放行）；已配置时用 `hmac.compare_digest` 恒定时间比较，失败返回 403。
- 两处维护接口（`clean-ticks`、`backfill`）统一调用该函数，删除各自的 `getattr(..., "citic_futures_admin_2026")` 兜底。

**影响**：旧默认令牌已失效。需在 `.env` 设置 `FUTURES_MAINTENANCE_TOKEN` 后才能使用维护接口。

### 3. CORS 收紧

**问题**：`allow_origins=["*"]` 与 `allow_credentials=True` 同时启用（互斥且危险）。

**改动**：新增 `resolve_cors_origins()`，从 `system.cors_origins` 解析逗号分隔来源，默认仅 `127.0.0.1:8000` 与 `localhost:8000`；检测到 `*` 时告警并回退到本机地址。`allow_methods` 收敛为 `GET/POST/DELETE/OPTIONS`，`allow_headers` 收敛为 `Content-Type, X-Admin-Token`。

### 4. 会话 Cookie 与密钥

- 登录 Cookie 新增 `secure` 标记：仅当请求经 HTTPS（或 `X-Forwarded-Proto: https`）时置位，避免本地 HTTP 调试时 Cookie 无法回传。
- `security._get_secret()` 改为三级优先：`FUTURES_SESSION_SECRET` 环境变量 > `config/session_secret.key` > 随机生成（**不再自动落盘**，此前会自动写明文密钥文件）。
- 新增 `config.get_session_secret()` 供外部调用。

### 5. tools_api 端点补鉴权

**问题**：`/api/v1/tools/*` 四个只读端点（manifest / quote / bars / signal）完全匿名可访问，可读取任意合约行情与信号。

**改动**：`APIRouter(dependencies=[Depends(require_user)])`，全部端点要求登录态。未登录返回 401。

### 6. Tick 清理调度器接通

**问题**：`DataRetentionManager.start_scheduler()` 全仓库只有定义、**零调用点**——每日 Tick 清理从未执行，过期数据只能靠手动调 HTTP 接口清理，MySQL 持续膨胀。

**改动**：
- `main.py` startup 中在 `ws_manager.set_loop(loop)` 之后调用 `retention_manager.start_scheduler(loop)`（默认每日 02:30）。
- `main.py` shutdown 中调用 `retention_manager.stop_scheduler()`。

### 7. 后台回填线程补异常边界

**问题**：`routes.py` 中 `maintenance/backfill` 派发的两个后台线程无 `try/except`，异常静默丢失。

**改动**：两处 `_task()` 包裹 `try/except` + `logger.exception`，并给线程命名便于排查。

### 8. 遗留文件归档

- `_tmp_chart.js`（135KB，2026-09-13 遗留调试片段）→ 移至 `backups/_tmp_chart_legacy_20260913.js`。
- 新增 `.gitignore` 覆盖 `backups/`、`*.log`、`_tmp_*.js` 等。

## 第二轮：测试补全与 CTP 重连

### 9. CTP 行情断线重连看门狗

**问题**：`CTPMarketCollector` 的 `OnFrontDisconnected` 仅置标志、记一条日志，既不告警也不重连。CTP 库自带重连在部分网络故障下会失效，且**登录失败不会自动重试**——一旦断开，行情静默停止，页面与引擎都拿不到数据，且没有任何提示。

**改动**（`backend/collector/ctp_collector.py`）：
- `CTPMdHandler` 新增 `last_tick_at`（每笔行情刷新），断开/登录失败时补发 `notifier` 告警（`CTP_MD_DISCONNECTED` / `CTP_MD_LOGIN_FAILED`），登录成功补发 `CTP_MD_LOGGED_IN`。
- 抽出 `_connect()`（建实例 + 注册 + Init），`_reconnect()` 会**先 Release 旧实例再重建**，避免句柄泄漏。
- 新增 `CTPMarketCollector._watchdog_loop()` 监督线程：每 5 秒检查一次，判定条件为「未连接/未登录」或「连接正常但长时间无行情（> 4×`STALE_DATA_SECONDS`）」，触发重连并按指数退避（1s → 30s 封顶）。
- **仅在交易时段判定**（`_is_trading_time()`），避免夜盘/休市静默被误判为故障而反复重连。
- `stop()` 先停看门狗、再 Release；重连过程中的任何异常都被吞掉并记日志，确保看门狗线程不会因一次失败而退出。

### 11. 修复 `test_minute_gap_repair` 的失败断言

**结论：实现是对的，测试断言过时。**

`repair_minute_gaps` 的文档字符串明确写着「**按历史源修正已收盘K线的行情字段**」，其设计意图就是让上游数据覆盖本地已落库的收盘K线——因为本地引擎冷启动会吞掉当分钟已有的成交量（第一笔快照累计量被当作基线），夜盘/开盘边界尤其明显，不纠偏则开盘分钟量永久偏小。

原测试断言已存在的 K 线（`999`）应保持不变，与实现意图相反。已改为断言被正确覆写为上游值（`741`），并补注释说明原因。

**另新增** `test_cutoff_bars_are_never_touched`：钉死契约的另一半——cutoff（近 2 分钟）之内的K线属实时引擎属地，历史源**不得覆写也不得补入**。该测试同时验证了「真实缺口应补入」与「cutoff 内不触碰」两个行为。

> 注意上游时间戳会整体前移 1 分钟（新浪以结束时间标记），写测试时容易踩错位，已在测试注释中标明。
