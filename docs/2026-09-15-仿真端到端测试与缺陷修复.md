## 3. 发现的缺陷与修复

### 缺陷 1（最严重）：就绪状态抖动，批量报单只有第一笔能通过

**现象**：服务端 `GET /api/v1/trade/live/status` 的 `ready` 在 True/False 间反复翻转，8 次采样有 3 次为 False，`sync_age` 在 2s/10s/12s 间跳变。

**根因**：`ctp_trader.py::request_reconcile()` 无条件执行 `self.reconciled = False`，而该方法被**5 秒周期心跳**和**每一次报单/成交回报**调用。`_sync_loop` 每轮开头同样清零 `reconciled`。于是对账完成到下一次心跳之间只有极短窗口是就绪的。

**后果**（这是紧急退出最不能失效的场景）：
- 单笔报单被随机拒绝；
- **批量报单（一键全平、批量撤单）只有第一笔能通过，后续全部以"柜台未就绪"被拒**。

**修复**：把"请求刷新"与"状态不确定"两种语义分开。

```python
def request_reconcile(self):
    """请求一次柜台对账: 只刷新快照, **不**改变就绪状态。"""
    self._sync_requested.set()

def mark_uncertain(self):
    """本地出现结果不确定的报单 (发送/撤单调用异常): 立即置为未就绪, 直到对账澄清。"""
    self._uncertain_seq += 1
    self.reconciled = False
    self._sync_requested.set()
```

`_sync_loop` 改为用序号前后比较决定是否恢复就绪：

```python
uncertain_at_start = self._uncertain_seq
try:
    ...
    live_trader.reconcile(snapshot, self.spi.trading_day)
    self.last_sync = time.monotonic()
    self.sync_error = ""
    self.reconciled = self._uncertain_seq == uncertain_at_start
except Exception as exc:
    self.sync_error = str(exc)
    self.reconciled = False
    logger.exception("CTP 对账失败，禁止新报单")
```

`live_trader.py` 中"发送/撤单调用异常"的分支由 `request_reconcile()` 改为 `mark_uncertain()`，语义才正确。

**验证**：修复后 HTTP 采样 8/8 全为 True；新增 `tests/test_live_readiness.py`（7 项）覆盖"请求对账不影响就绪""结果不确定阻断后续报单""连发两单第二单不被拒""close_all 每腿都提交"。

### 缺陷 2：SHFE/INE 一键全平未按平今/平昨拆单

**现象**：代码注释写着"按 `max_order_volume` 拆单（平仓豁免单笔上限，但拆单更安全）""平今/平昨判定（SHFE/INE 必须区分）"，但 `close_all` 的实现**并未拆单**，也未区分平今/平昨。

**后果**：上期所/能源中心持仓同时含今仓与昨仓时，若按单笔量整笔报 `CLOSE_TODAY`，今仓不足会被柜台直接拒单 → **一键全平部分失败**，正是紧急退出时最不能出现的状况。

**修复**：新增 `_plan_close()` 把一次平仓拆成 `[(offset, volume)]` 腿，`close_all` 逐腿报单：

```python
def _plan_close(self, instrument, pos_key, volume, remaining_today) -> List[tuple]:
    if get_exchange(instrument) not in ("SHFE", "INE"):
        return [(OffsetFlag.CLOSE, volume)]
    today_left = max(0, int(remaining_today.get(pos_key, 0) or 0))
    if today_left <= 0:
        return [(OffsetFlag.CLOSE_YEST, volume)]
    if today_left >= volume:
        return [(OffsetFlag.CLOSE_TODAY, volume)]
    return [(OffsetFlag.CLOSE_TODAY, today_left),
            (OffsetFlag.CLOSE_YEST, volume - today_left)]
```

`remaining_today` 随报单递减，保证拆腿之和不超过今仓/昨仓各桶可用量。

**验证**：新增 `tests/test_live_close_split_and_cancel.py::TestCloseSplitPlan`（6 项）与 `TestCloseAllSplitsOrders`（3 项）。典型用例：5 手持仓（今 1 昨 4）按单批 3 手全平 → `[("CLOSE_TODAY",1), ("CLOSE_YEST",2), ("CLOSE_YEST",2)]`。

### 缺陷 3：撤单失败回报被静默丢弃

**现象**：`OnRspOrderAction` 收到柜台撤单应答时**完全忽略 ErrorID**，只无条件请求对账。

**后果**：柜台拒绝撤单（例如"当前状态不可撤"）时，本地委托记录卡在 `CANCELLING`，操作人既看不到失败原因，也无法判断该委托是否仍在交易所队列中——存在误以为已撤单而重复下单的风险。

**修复**：`OnRspOrderAction` 显式检查 `ErrorID`，记日志、发告警，并回调前台回退状态：

```python
def OnRspOrderAction(self, action, info, request_id, last):
    if info and info.ErrorID != 0:
        logger.error("CTP 撤单被柜台拒绝: %s (ErrorID: %s)", info.ErrorMsg, info.ErrorID)
        notifier.notify("CTP_CANCEL_REJECTED", f"撤单被柜台拒绝: {info.ErrorMsg}",
                        "WARNING", "ctp_trader")
        if self.executor:
            self.executor.cancel_rejected(action, info.ErrorMsg)
    if self.executor:
        self.executor.request_reconcile()
```

新增 `CTPTradeExecutor.cancel_rejected()` 与 `LiveTrader.on_cancel_rejected()`：把 `CANCELLING` 回退为 `SUBMITTED` 并写入 `reject_reason`；已是终态则不覆盖；未知委托直接忽略；**全程吞异常**，回报处理绝不外抛。

**验证**：`TestCancelRejectionHandling`（5 项）：回退为 SUBMITTED 并写入原因、不覆盖终态、未知委托忽略、executor 委派、异常不外抛。

### 缺陷 5（生产，严重）：CTP 合约代码大小写错误导致行情订阅静默失效

**现象**：端到端测试拿不到 CTP 行情（`CTP MD 无推送`），脚本回退到 Redis 里的陈旧价，报单被交易所拒绝：

```
49:已撤单报单被拒绝SHFE:价格超出涨停板
```

**排查过程**（一路排除后定位到大小写）：

1. 先怀疑是休市时段问题 → 开盘后复测仍失败；
2. 再怀疑是报单价格问题 → 换成活跃合约 FU2611 后仍失败；
3. 查数据库发现 **FU2610 当日无任何行情**（最新数据停在 09-14 14:59），FU2611 才是活跃合约；
4. 直接对比订阅大小写，**一击命中**：

```
FU2611 -> {"error": "等待行情超时"}                      # 大写: 永远收不到
fu2611 -> {"last": "4099.0", "bid": "4099.0", ...}      # 小写: 立即收到
```

**根因**：`backend/collector/ctp_collector.py:70` 直接把配置里的合约代码丢给 `SubscribeMarketData`，而配置 `config/instruments.yaml` 写的是大写 `FU2610` / `BU2610`。**CTP 对合约代码大小写敏感**：SHFE/INE/DCE/GFEX 必须小写，CZCE/CFFEX 才用大写。

**危害**：行情订阅用错大小写**不会报错**——`OnRspSubMarketData` 返回成功，但**永远不会推送**。生产环境 `feed=ctp` 时，所有 SHFE/INE/DCE 合约的行情都会静默失效，且日志上看不出任何异常。这属于最危险的一类缺陷：没有报错，只有沉默。

**修复**：把交易侧已有的大小写规则提取为公共函数，三处调用点统一复用：

```python
# backend/common/product_specs.py
def to_ctp_instrument(symbol: str) -> str:
    """把内部合约代码规范化为 CTP 接口要求的大小写。

    CTP 对合约代码**大小写敏感**, 且各交易所规则不同:
      - CZCE / CFFEX: 大写 (SR601 / IF2601)
      - SHFE / INE / DCE / GFEX: 小写 (fu2611 / sc2601 / jm2701)
    """
    s = (symbol or "").strip()
    if not s:
        return s
    return s.upper() if get_exchange(s) in ("CZCE", "CFFEX") else s.lower()
```

调用点：
- `ctp_collector.py`（行情订阅）← 本次缺陷所在
- `ctp_trader.py` 报单 / 撤单（原为内联三元表达式，改为复用）
- `scripts/live_sim_e2e.py` 行情订阅

**验证**：`FU2611→fu2611`、`JM2701→jm2701`、`SR601→SR601`、`IF2601→IF2601`；`fetch_quote('FU2611')` 修复后立即取到行情 4099。

### 缺陷 6（测试工具）：持仓快照异步刷新导致误判

**现象**：
- 委托回报 `FILLED`，但"持仓随成交增加"检查读到 `before=0 after=0`；
- 因读不到今仓，平仓标志退化为 `CLOSE` 而非 `CLOSE_TODAY`，报单被拒"无对应持仓"；
- 05b 挂第 2 笔被动单被误拦：`开仓后总持仓 3 超过单合约持仓上限 2`。

**根因**：柜台持仓查询是**异步**的。成交回报只会"置位对账请求"，快照更新需要等下一轮对账。测试脚本直接读 `get_snapshot()`，拿到的是成交前的旧持仓。

**修复**：新增轮询式等待，替代"请求一次 + 立即读"：

```python
def _wait_position(trader, symbol, direction, expect, timeout=25.0):
    """反复触发对账, 直到持仓达到期望手数。"""
    last = None
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        trader.executor.request_reconcile()
        time.sleep(0.8)
        last = _position_volume(trader, symbol, direction)
        if last >= expect:
            return True, last
    return False, last

def _wait_position_zero(trader, symbol, direction, timeout=20.0):
    """反复对账直到该方向持仓归零 (平仓后快照滞后会让后续开仓被上限误拦)。"""
```

并在 05b 阶段加入**前置清理**（先确认持仓归零，否则主动全平），避免上一阶段残留持仓污染本阶段。

此外新增 `--reset-daily-counts`：当日委托/撤单计数由 `trading_state` 持久化（重启不可绕过风控），多轮测试会耗尽配额，测试时需显式重置。**首次触发该上限时反而真实验证了"单日报单笔数上限"这条边界**。

## 7. 遗留风险

1. **模拟盘与实盘共用同一个 `PreTradeRiskManager` 实例**，长期应拆成两个实例或两套默认值；
2. 合约大小写映射：`ctp_trader.py` 对 CZCE/CFFEX 保持大写、其余转小写，`product_specs.get_exchange()` 映射缺失会直接导致报单被拒；
3. `UNKNOWN` 委托会让 `reconcile()` 抛异常 → `reconciled=False` → 全部报单被拒，这是**有意的安全设计**，处置靠人工核对柜台后手工消解，**严禁改代码绕过**；
4. `max_order_volume` 只卡开仓不卡平仓是**有意豁免**（历史故障：裸空 177 手被卡死平不掉），改风控时必须保留；
5. 告警 Webhook 未配置，仿真期故障无主动通知。
