### 0.2 三个必须先解决的硬约束

这三条不解决，后面的测试流程无法真正跑通：

1. **无配置隔离**：切仿真/生产靠手改 `config/settings.yaml` 的 `md_address`/`td_address`/`broker_id` 三处 + `.env` 账号。手工操作极易把仿真参数带进生产，或误连生产柜台。

2. **无结构化流水表**：订单、成交、持仓序列化为 JSON 塞在一个大字段里。无法用 SQL 做逐笔对账、无法按合约/日做盈亏归因、无法跨账户查询。**柜台对账是本流程的核心动作，没有表就无法验收。**

   → 必须外置为 YAML 配置，并支持**按阶段调整**（灰度放量的本质就是逐步抬高这些阈值）。

### 1.3 步骤二：结构化流水表（对账的地基）

**具体动作**：新增三张表（`backend/models/database.py`），并**双写**——现有 JSON 存储保留（不破坏兼容），同时追加写入结构化表。

```sql
-- 委托流水
CREATE TABLE order_record (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  order_ref     VARCHAR(64)  NOT NULL,      -- 本地键: day_front_session_ref
  gateway_ref   VARCHAR(32),                -- 柜台 OrderRef
  broker_id     VARCHAR(16),
  investor_id   VARCHAR(32),
  trading_day   VARCHAR(8),
  front_id      INT,
  session_id    INT,
  order_sys_id  VARCHAR(32),
  exchange      VARCHAR(8),
  instrument_id VARCHAR(16)  NOT NULL,
  direction     VARCHAR(4),                 -- BUY / SELL
  offset_flag   VARCHAR(12),                -- OPEN / CLOSE / CLOSE_TODAY / CLOSE_YEST
  price         DECIMAL(18,6),
  volume        INT,
  traded_volume INT DEFAULT 0,
  status        VARCHAR(12),                -- SENDING/SUBMITTED/PARTIAL/FILLED/CANCELLING/CANCELLED/REJECTED/UNKNOWN
  status_msg    VARCHAR(255),
  owner         VARCHAR(32),
  submit_time   DATETIME,
  update_time   DATETIME,
  UNIQUE KEY uq_order_ref (order_ref),
  KEY idx_day_instrument (trading_day, instrument_id),
  KEY idx_status (status)
);

-- 成交流水
CREATE TABLE trade_record (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  trade_key     VARCHAR(96) NOT NULL,       -- day:exchange:TradeID
  trade_id      VARCHAR(32),
  order_ref     VARCHAR(64),
  order_sys_id  VARCHAR(32),
  exchange      VARCHAR(8),
  instrument_id VARCHAR(16),
  direction     VARCHAR(4),
  offset_flag   VARCHAR(12),
  price         DECIMAL(18,6),
  volume        INT,
  trade_time    DATETIME,
  trading_day   VARCHAR(8),
  UNIQUE KEY uq_trade_key (trade_key),
  KEY idx_day_instrument (trading_day, instrument_id)
);

-- 持仓快照（每次对账落一份，可做日间归因）
CREATE TABLE position_snapshot (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  trading_day   VARCHAR(8),
  snapshot_time DATETIME,
  investor_id   VARCHAR(32),
  instrument_id VARCHAR(16),
  posi_direction VARCHAR(4),                -- 2=多头 3=空头
  position      INT,
  today_position INT,
  yd_position   INT,
  long_frozen   INT,
  short_frozen  INT,
  position_cost DECIMAL(18,6),
  use_margin    DECIMAL(18,2),
  position_profit DECIMAL(18,2),
  KEY idx_day_instrument (trading_day, instrument_id)
);
```

**落库位置**：`live_trader.py` 的 `on_order()` / `on_trade()` / `reconcile()` 三处，在 `self._save()` 前后追加结构化写入。

**关键脚本/工具**：
- 迁移：`alembic revision --autogenerate -m "add order/trade/position tables"`
- ⚠️ 注意：现有初始迁移的 `upgrade()` 是空 `pass`，实际建表靠 `init_db()` 的 `create_all`。新增表沿用 `create_all` 也能建起来，但**生产环境应走 alembic 显式迁移**，避免 `create_all` 不可控地改动既有表。

**常见风险点**：
- 双写失败会导致 JSON 与表不一致 → 必须把结构化写入放在同一事务，或失败时置 `executor.reconciled = False` 阻断交易（沿用现有机制）。
- `UNIQUE KEY` 冲突：柜台重发回报会重复 `order_ref` → 用 `INSERT ... ON DUPLICATE KEY UPDATE`。

### 1.4 步骤三：风控阈值外置

**具体动作**：在 `config/settings.yaml` 新增 `risk` 段，改造 `PreTradeRiskManager` 从配置读取。

```yaml
risk:
  # 阶段化阈值：灰度放量靠这里递增
  max_order_volume: 1           # 阶段1: 1手 → 阶段4: 20手 → 全量: 50手
  max_position_volume: 2        # 阶段1: 2手 → 阶段4: 40手
  margin_ratio: 0.12            # 可略高于交易所实际，留安全垫
  max_daily_loss_ratio: 0.01    # 阶段1: 1% → 全量: 5%
  max_cancel_count: 20          # 阶段1: 20次/日 → 全量: 400次/日
  # 新增：实盘专属保护
  live_enabled: false           # 总开关，false 时实盘接口一律拒绝
  allowed_instruments: []       # 白名单，空=不限制；灰度期只放 FU2610
  daily_order_limit: 20         # 单日总报单笔数上限
  fat_finger_pct: 0.02          # 报单价偏离最新价超过 2% 拒绝
```

**改造 `risk_manager.py`**：

```python
def __init__(self, ...):
    risk_cfg = getattr(cfg, "risk", None)
    self.max_order_volume = int(getattr(risk_cfg, "max_order_volume", 50))
    self.max_position_volume = int(getattr(risk_cfg, "max_position_volume", 200))
    self.margin_ratio = Decimal(str(getattr(risk_cfg, "margin_ratio", "0.12")))
    self.max_cancel_count = int(getattr(risk_cfg, "max_cancel_count", 400))
```

**新增两项检查**（现有六项之外）：

```python
# 7. 报单价格偏离保护（防手滑/防程序 bug 报出天价）
if req.offset == OffsetFlag.OPEN and last_price:
    dev = abs(req.price - last_price) / last_price
    if dev > self.fat_finger_pct:
        return False, f"报单价 {req.price} 偏离最新价 {last_price} 达 {dev*100:.2f}%，超过 {self.fat_finger_pct*100:.1f}% 保护阈值"

# 8. 合约白名单
if self.allowed_instruments and req.instrument not in self.allowed_instruments:
    return False, f"合约 {req.instrument} 不在实盘白名单内"
```

> ⚠️ **白名单必须同时校验平仓**。历史故障：`max_order_volume` 曾只卡开仓不卡平仓导致裸空平不掉；白名单如果同样漏掉平仓分支，会出现"能开的合约不让平"，风险远大于开仓。**开仓做白名单限制，平仓豁免**。

**常见风险点**：
- **模拟盘与实盘共用同一实例**：`live_trader.py:18` 与 `paper_trader` 各自 `PreTradeRiskManager()`，改造后参数一致；如果希望模拟盘保持宽松、实盘严格，需要给实盘传独立配置。
- `margin_ratio=0.12` 是**固定值**，但交易所对不同品种/不同时期保证金率不同（临近交割月会大幅提高）。固定 12% 会在保证金上调时导致"风控认为够、柜台实际不足"的拒单。
  **缓解**：从柜台资金快照反算实际占用率（`CurrMargin / 持仓市值`），不依赖固定值做唯一判据；同时在检查 3 之外，保留柜台侧拒单为最终兜底。

#### 步骤五：下单链路验证（最小手数、最保守参数）

**第一次报单必须满足**：`max_order_volume=1`、只报 `FU2610`（白名单只放这一个）、价格设在**远离盘口的限价**（例如低于买一 10 个跳），确保**不会成交**——这样只验证"报单是否到达柜台"，不引入成交和持仓复杂度。

| 动作 | 接口 | 期望结果 |
|---|---|---|
| 确认就绪 | `GET /api/v1/trade/live/status` | `ready: true`，`settlement_confirmed: true`，`reconciled: true` |
| 报一笔不成交的限价单 | `POST /api/v1/trade/live/order` | 返回 `order_ref`、`status: SUBMITTED` |
| 查本地委托 | `GET /api/v1/trade/live/orders` | 新委托状态 `SUBMITTED`，`gateway_code: 0` |
| **查柜台委托（关键）** | 通过交易软件或柜台查询 | **必须能看到同一笔委托**，`OrderSysID` 非空 |
| 交叉核对字段 | 对比本地记录 vs 柜台 | 合约/方向/开平/价格/手数 完全一致 |

**这是本模块最核心的验收点**：本地报单成功 ≠ 柜台收到。必须以柜台记录为准。

| ErrorID 段 | 含义 | 处置 |

| `3` / `31` | 未登录 / 非法登录 | 检查登录流程 |
| `42` | 重复报单（OrderRef 重复） | 检查 `flow_path` 是否被污染；跨交易日 OrderRef 是否重置 |
| `50` 段 | 平仓仓位不足 / 开平标志错误 | 检查 `CombOffsetFlag`；郑商所/中金所与上期所的平今机制不同 |
| `63` | 资金不足 | 检查保证金；对照柜台可用资金 |
| `73` | 合约不存在 | 检查 `InstrumentID` 大小写——**代码中对 CZCE/CFFEX 保持大写，其余市场转小写**（`ctp_trader.py:229`），配错会导致报单被拒 |

**合约大小写是高频坑**：`ctp_trader.py:229` 和 `:275` 都有 `if get_exchange(...) in ("CZCE","CFFEX") else .lower()` 的逻辑。如果 `backend/common/product_specs.py` 的交易所映射缺了某品种，大小写就会错。**上线前逐一核对白名单合约的映射结果**。

#### 步骤六：撤单链路验证

| 动作 | 接口 | 期望结果 |
|---|---|---|
| 撤上一步的挂单 | `DELETE /api/v1/trade/live/order/{order_ref}` | `status: cancel_submitted`，`code: 0` |
| 查本地状态 | `GET /api/v1/trade/live/orders` | 状态转为 `CANCELLED` |
| **查柜台状态** | 交易软件 | 委托已撤销 |
| 重复撤同一笔 | 再次 DELETE | 应返回 `当前委托状态不可撤`，不产生二次撤单请求 |
| 撤单计数验证 | 连续撤 N 次 | 达到 `max_cancel_count` 后拒绝；`risk.cancel_counts` 落库 |

**撤单定位四要素**（`ctp_trader.py:262-284`）：`OrderRef` + `FrontID` + `SessionID` + `OrderSysID`。
**风险点**：`FrontID`/`SessionID` **每次登录都会变**。如果程序在盘中重连过，旧委托的 `FrontID`/`SessionID` 会失效，导致撤单失败。**代码已从 record 中取而非从 spI 当前值取**（`:272-273`），这是正确的——但前提是 record 里存的确实是**报单当时**的 FrontID/SessionID。
**验证方法**：盘中主动重连一次（重启服务或断网），再撤一笔跨重连的旧委托。

#### 步骤七：成交回报验证

| 动作 | 操作 | 期望结果 |
|---|---|---|
| 报一笔**会成交**的单（对手价） | 买一价报 1 手（白名单内合约） | 返回 SUBMITTED |
| 等待成交回报 | — | 日志出现 `CTP 实盘成交流水`；`OnRtnTrade` 触发 |
| 查本地成交 | 结构化 `trade_record` 表 / `get_snapshot()["trades"]` | 有成交记录，`TradeID` 非空 |
| 查本地委托状态 | `GET /api/v1/trade/live/orders` | `status: FILLED`，`traded_volume` = 委托手数 |
| **查柜台成交** | 交易软件成交明细 | `TradeID`、价格、手数**逐字段一致** |
| 部分成交场景 | 报 5 手，可能只成交 3 手 | 委托状态 `PARTIAL`，`traded_volume=3`，剩余 2 手仍可撤 |

**成交价核对是本步骤的验收核心**。用结构化表做 SQL 对账：

```sql
-- 本地成交 vs 柜台成交逐笔核对（人工填柜台导出结果做比对）
SELECT trading_day, instrument_id, direction, price, volume, trade_id
FROM trade_record
WHERE trading_day = '20260915'
ORDER BY trade_time;
```

**风险点**：
- **成交回报可能乱序/重复到达**。`_apply_trade` 用 `day:exchange:TradeID` 做幂等键（`live_trader.py:186`），正确。
- **`on_trade` 落库失败会置 `sync_error` 但不阻断**（`ctp_trader.py:357-364`）。这意味着可能出现"柜台已成交、本地漏记"。**必须靠每次对账（`reconcile`）全量比对来兜底**，不能只依赖实时回报。
- **盘中成交后立即撤单**：部分成交后的剩余量撤单，需要处理 `PARTIAL → CANCELLING → CANCELLED` 的状态跃迁。

#### 步骤八：账户与持仓查询交叉核对

| 动作 | 接口 | 期望结果 |
|---|---|---|
| 查本地资金 | `GET /api/v1/trade/live/account` | 返回 `Balance`/`Available`/`CurrMargin`/`FrozenMargin` |
| 查柜台资金 | 交易软件 | **逐字段一致**（允许分秒级时点差异） |
| 查本地持仓 | `GET /api/v1/trade/live/status` 的 snapshot | 持仓方向/手数/今仓/昨仓/保证金 |
| 查柜台持仓 | 交易软件 | 逐字段一致 |
| 重点核对 | 今仓 vs 昨仓 | `TodayPosition` / `YdPosition` 分开核对——**这直接决定平今/平昨标志是否正确** |

**风险点**：
- 上期所（SHFE/INE）**必须区分平今和平昨**，且平今手续费往往远高于平昨。`ctp_trader.py:239-244` 有 `CLOSE_TODAY`/`CLOSE_YEST` 分支，但**当前前端/接口传入的 `offset` 由调用方决定**——如果调用方总是传 `CLOSE`，柜台会按自己的规则处理，可能与预期不符。
  **动作**：明确平仓标志生成策略。对 SHFE/INE，先查持仓快照的 `TodayPosition`，若 ≥ 平仓量则用 `CLOSE_TODAY`，否则用 `CLOSE_YEST`。
- **资金快照只在 `sync_loop` 每 5 秒轮询**（`ctp_trader.py:315`）。刚成交后立刻查资金可能是旧值。
  **验收方法**：成交后等 ≥ 6 秒再查，或主动 `request_reconcile()` 触发。

#### 步骤九：对账一致性验收（模块一收口）

**具体动作**：
1. 跑满一个完整交易日（含夜盘）。
2. 收盘后导出柜台对账单。
3. 用 SQL 汇总本地 `order_record` / `trade_record`，与柜台对账单逐笔比对。
4. 生成差异报告，差异必须为 **0 笔**。

**验收判据**：

| 指标 | 要求 |
|---|---|
| 委托笔数差异 | 0 |
| 成交笔数差异 | 0 |
| 成交手数差异 | 0 |
| 成交金额差异 | 0.00（允许 ±最小变动价位×手数 的舍入） |
| 期末持仓差异 | 0 |
| 期末资金差异 | 0.00 |
| 状态为 `UNKNOWN` 的委托 | 0（有则必须人工核对柜台后手动消解） |

**常见风险点**：`reconcile()` 中有这段逻辑——若存在 `SENDING`/`UNKNOWN` 状态的委托，会 `raise RuntimeError("存在未确认报单，必须核对柜台记录后再恢复交易")`（`live_trader.py:216-217`），**导致 `reconciled=False`、`is_ready=False`、所有新报单被拒**。
这是**正确的安全设计**，但会造成"系统看起来卡死"。**处理手册**：
1. 查柜台该笔委托的真实状态（可能已成交/已撤/被拒）。
2. 若已终态，手工把 `trading_state` 中该笔记录状态改为终态。
3. 触发 `request_reconcile()`，恢复 `is_ready`。
4. **绝不允许**通过放宽代码来跳过这一步。

## 模块二：实盘与仿真环境的差异处理

### 2.1 六项核心差异对照

| 差异维度 | 仿真环境（SimNow 类） | 实盘环境 | 处理策略 |
|---|---|---|---|
| **撮合延迟** | 常人为注入 20–50ms，且不反映真实排队 | 真实排队，交易所撮合毫秒级，网络往返 1–30ms 波动 | 报单超时阈值设 ≥ 3s；**不依赖"报出去就成交"的假设** |
| **撮合规则** | 部分仿真对市价单/涨停板单直接全成 | 严格价格优先时间优先，涨跌停可能无法成交 | 只用限价单；不用市价单；涨跌停附近不报单 |
| **滑点** | 通常为 0 或固定值 | 真实滑点取决于流动性，随盘口深度变化 | **必须用真实盘口算预期滑点**；模拟盘 `paper_slippage_ticks` 默认 0，会系统性高估盈亏 |
| **手续费/保证金** | 多为 0 或简化 | 按品种/交易所精算，含平今加收、日内平仓优惠 | 从柜台实际扣费反推，逐品种校准；禁止用 0 手续费评估策略 |
| **风控阈值** | 柜台风控宽松，很少拒单 | 交易所 + 期货公司双重风控，可能因异常交易被限制 | 自建风控必须**严于**柜台，不能依赖柜台兜底 |
| **可用资金** | 常给虚拟大额资金 | 真实资金，且浮动盈亏实时影响可用 | 保证金占用需留安全垫（建议实际可用 ≥ 需要的 1.5 倍） |

### 2.2 延迟：必须实测，不能假设

**具体动作**：在 `live_trader.submit_live_order` 中埋点，记录三个时间戳并落库：

```python
t0 = time.perf_counter()                 # 风控检查通过
# ... 发送
t1 = time.perf_counter()                 # ReqOrderInsert 返回
# OnRtnOrder 回调中记录
t2 = time.perf_counter()                 # 收到柜台委托回报
# OnRtnTrade 回调中记录
t3 = time.perf_counter()                 # 收到成交回报
```

**指标**：
- `发送耗时 = t1 - t0`（本地调用耗时，正常 < 1ms）
- `委托确认延迟 = t2 - t1`（**关键**，正常 5–100ms）
- `成交回报延迟 = t3 - t1`

**阈值告警**：委托确认延迟 > 3s 触发告警——超过此值说明网络或柜台异常，此时报单可能已丢失，需人工介入。

**风险点**：`_sync_loop` 每 5 秒轮询一次（`ctp_trader.py:315`），且 `is_ready` 要求 `time.monotonic() - last_sync < 15`。如果一次对账因网络慢而超时（单次查询超时 10s，`ctp_trader.py:334`），四类查询最坏情况会耗时 40s+，**导致 `is_ready` 直接变 false、交易中断**。
**缓解**：把 `15` 秒改为可配置，并把它设为"至少 2 倍单轮对账最坏耗时"；同时缩短单次查询超时。

### 2.3 撮合与滑点：用真实盘口做基准

**具体动作**：
1. 录制一段真实 tick（开启 `save_raw_tick: true`，写入 `market_tick` 表）。
2. 用该 tick 回放模拟盘撮合，对比模拟成交价与同期真实盘口可实现价格。
3. 计算**系统性偏差**：模拟成交价 - 真实可实现价。偏差应接近 0 且方向随机（不是系统性有利）。

**校准模拟盘参数**：

```yaml
system:
  paper_fill_uses_opponent: true      # 保持 true，这是高仿真的关键
  paper_slippage_ticks: 1.0           # 从 0 改为实测量级
  paper_commission_per_lot: <实测值>  # 从 0 改为柜台真实费率
```

**风险点**：`paper_slippage_ticks=0`、`paper_commission_per_lot=0` 会让模拟盘**系统性高估盈利**。用这样的模拟结果去决定放量，等于用乐观数据做风险决策。
**判定方法**：如果模拟盘连续盈利但实盘同策略亏损，第一件事就是查这两个参数。

### 2.4 风控阈值：仿真与实盘必须分档

**原则**：**实盘阈值 ≤ 仿真阈值**，且灰度期远小于仿真期。

| 阈值 | 仿真期 | 灰度阶段1 | 灰度阶段4 | 全量 |
|---|---|---|---|---|
| `max_order_volume` | 50 | **1** | 20 | 50 |
| `max_position_volume` | 200 | **2** | 40 | 200 |
| `max_daily_loss_ratio` | 5% | **1%** | 3% | 5% |
| `max_cancel_count` | 400 | **20** | 100 | 400 |
| `daily_order_limit` | 不限 | **20 笔** | 100 笔 | 不限 |
| `fat_finger_pct` | 无 | **2%** | 2% | 2% |
| `allowed_instruments` | 全部 | **1 个合约** | 3 个 | 全部 |

**特别注意 `max_cancel_count`**：交易所有"频繁报撤单"异常交易认定标准。`max_cancel_count=400` 是按监管警示线设的，**在灰度期应大幅下调**（20 次/日），避免触碰交易所异常交易监控。

### 2.5 数据口径差异（本项目特有）

| 项 | 差异 | 处理 |
|---|---|---|
| 行情 `volume` | CTP `OnRtnDepthMarketData` 的 `volume` 在夜盘 21:00 **清零重新累计** | 顶栏累计成交用 `quote.volume`；VOL/当日统计用 1m bars，**两者不能混用** |
| 1m 时间语义 | 新浪源已统一平移到分钟**开始**；CTP 源需确认是否同样平移 | 上线前与新浪源结果对拍同一时段 |
| 高阶周期口径 | 1m 含集合竞价，5m/15m/日线口径不同 | **跨周期成交量不可直接相减** |
| 结算价 vs 收盘价 | 涨跌基准是 `prev_settle`（昨结算），不是昨收盘 | 前端涨跌颜色基准必须是 `prev_settle` |

## 模块四：灰度测试与分阶段上线策略

### 4.1 五个阶段总览

| 阶段 | 名称 | 时长 | 单笔上限 | 持仓上限 | 合约数 | 日报单上限 | 日亏熔断 | 放行条件 |
|---|---|---|---|---|---|---|---|---|
| S0 | 静态检查 | 1 天 | — | — | — | — | — | 检查清单 34 项全绿 |
| S1 | 单笔试跑 | 3 交易日 | 1 手 | 2 手 | 1 | 20 笔 | 1% | 零错单、对账 100% 一致 |
| S2 | 小资金放量 | 3 交易日 | 5 手 | 10 手 | 1 | 50 笔 | 2% | 对账一致、滑点达标 |
| S3 | 中等放量 | 3 交易日 | 20 手 | 40 手 | 3 | 100 笔 | 3% | 对账一致、无异常交易提示 |
| S4 | 接近全量 | 5 交易日 | 50 手 | 200 手 | 全部 | 不限 | 5% | 连续 5 日无 P0 事件 |

**每档观察期不少于 3 个交易日**——这是覆盖"夜盘切换 + 结算 + 逐日重置"完整周期的最小单位。少于 3 天，`day_start_equity`、`cancel_counts`、`trading_day` 的跨日重置逻辑就没被验证过。

### 4.2 每档的进入/退出判据

#### S1 单笔试跑（最关键，暴露问题最多）

**动作**：
1. 阈值设为 `max_order_volume=1`、`max_position_volume=2`、白名单只放 `FU2610`。
2. 每日做固定动作序列：
   - 09:00 开盘后：报 1 手不成交的远价单 → 撤单
   - 10:00：报 1 手对手价单 → 等成交 → 核对成交
   - 14:00：平掉持仓 → 核对持仓归零
   - 收盘后：导出柜台对账单 → 与本地核对
3. 每日记录：委托笔数、成交笔数、错单数、延迟、撤单数、对账差异。

**放行条件（全部满足）**：
- ✅ 累计错单（`REJECTED`）= 0
- ✅ 对账差异 = 0（笔数、手数、金额、持仓、资金）
- ✅ `UNKNOWN` 状态委托 = 0
- ✅ 委托确认延迟 P99 < 1s
- ✅ 无 `CTP_TRADER_DISCONNECTED` 事件，或发生但重连后自动恢复且无丢单
- ✅ 平今/平昨标志正确（核对柜台成交的 `CombOffsetFlag`）

**一票否决项**：出现任何一笔 `UNKNOWN` 未消解、或任何一笔"柜台有、本地无"。**必须停下来查清根因，不得带病放量。**

#### S2 小资金放量

**动作**：`max_order_volume=5`、`max_position_volume=10`。新增场景：
- 部分成交（报 5 手，可能只成 3 手）
- 部分成交后撤剩余
- 同日多次开平
- **盘中主动重启服务**，验证重启后对账恢复与旧委托可撤

**放行条件**：同 S1，加：
- ✅ 部分成交场景账务正确（`traded_volume` 与持仓/资金一致）
- ✅ 重启后 60 秒内恢复 `is_ready=true`
- ✅ 跨重连的旧委托可正常撤销（验证 FrontID/SessionID 取自 record 的设计）

#### S3 中等放量

**动作**：`max_order_volume=20`、`max_position_volume=40`，白名单放到 3 个合约（覆盖不同交易所，**必须包含一个 CZCE 或 CFFEX 合约**以验证大小写映射）。

**放行条件**：加：
- ✅ 多合约并发报单无串单（`order_ref` 不冲突）
- ✅ CZCE/CFFEX 合约大小写映射正确
- ✅ 无交易所异常交易提示（频繁报撤单）
- ✅ 滑点实测值在预期范围内（与仿真对比偏差 < 2 跳）

#### S4 接近全量

**动作**：`max_order_volume=50`、`max_position_volume=200`，白名单放开到全部目标合约。

**放行条件**：
- ✅ 连续 5 个交易日零 P0 事件
- ✅ 单日最大回撤未触及熔断线
- ✅ 对账一致性连续 5 日 100%
- ✅ 人工签字确认

### 4.3 每日固定动作（S1–S4 通用）

**开盘前（08:45 / 20:45）**：
1. 服务健康检查：`/api/v1/health`、`/api/v1/feed-status`
2. 柜台就绪：`/api/v1/trade/live/status` 的 `ready` 必须为 `true`
3. 核对柜台可用资金与持仓 vs 本地快照
4. 确认当日交易时段（有夜盘/无夜盘的合约分别确认）

**收盘后（15:15 / 23:30）**：
1. 确认无未成交挂单（有则撤净）
2. 导出柜台对账单
3. 跑对账脚本，生成差异报告
4. 记录当日指标到测试日志
5. **确认持仓是否符合预期**（隔夜仓需要明确决策：留还是平）

### 4.4 熔断（自动降档）条件

任一条件触发，**立即回退到上一阶段**，并暂停至少 1 个交易日：

## 模块五：监控告警与异常处理

### 5.1 监控指标体系

**必须监控的三层指标**：

#### 连接层

| 指标 | 采集方式 | 告警阈值 |
|---|---|---|
| 行情前置连接状态 | `ctp_collector` 的 `is_connected` | 断开立即告警 |
| 交易前置连接状态 | `spi.is_connected` | 断开立即告警 |
| 登录状态 | `spi.is_logged_in` | 断开立即告警 |
| 结算确认 | `spi.settlement_confirmed` | 未确认禁止报单 |
| 对账状态 | `executor.reconciled` | false 立即告警 |
| 对账新鲜度 | `time.monotonic() - last_sync` | > 15s 告警（**这是 `is_ready` 的组成部分**） |
| tick 新鲜度 | 最大 tick 时间与当前时间差 | > 30s 告警（交易时段内） |

#### 交易层

| 指标 | 告警阈值 |
|---|---|
| 委托确认延迟 P50/P99 | P99 > 1s 警告，> 3s 严重 |
| 拒单率 | > 5% 警告，> 20% 严重 |
| `UNKNOWN` 状态委托数 | **> 0 立即严重告警** |
| 日累计报单笔数 | > 阈值 80% 警告 |
| 当日撤单笔数 | > `max_cancel_count` 80% 警告 |
| 当日亏损比例 | > 熔断线 80% 警告 |
| 持仓集中度 | 单合约占用保证金 > 总权益 50% 警告 |

#### 系统层

| 指标 | 告警阈值 |
|---|---|
| MySQL 联通 | 断开严重 |
| Redis 联通 | 断开严重 |
| 落库失败（`sync_error` 非空） | 立即严重 |
| `trading_state` 乐观锁冲突 | 出现即告警（意味着多进程写同一账户） |
| 进程存活 | 退出立即告警 |

### 5.3 断线重连

**已有能力**：
- 行情：`_watchdog_loop` 看门狗，退避 1s→30s，30s 无数据判假死（仅在交易时段判定）—— `ctp_collector.py:164-204`
- 交易：`OnFrontDisconnected` 会重置全部就绪标志并置 `reconciled=False`，触发告警 —— `ctp_trader.py:50-58`

**⚠️ 关键缺口：CTP 交易前置断开后，没有自动重连逻辑。** `OnFrontDisconnected` 只是把标志位置 false，**没有重新 `Init()` 或 `RegisterFront()`**。

**修复动作**：新增交易连接看门狗线程：

```python
def _td_watchdog_loop(self):
    """交易前置看门狗：断开且处于交易时段时，退避重连。"""
    backoff = 1.0
    while not self._stopped.is_set():
        if self._stopped.wait(2):
            break
        spi = self.spi
        if spi and spi.is_connected:
            backoff = 1.0
            continue
        if not FuturesTradingCalendar.is_trading_time(now):
            continue                      # 非交易时段不重连，避免无意义刷日志
        logger.warning("CTP 交易前置断开，%s 秒后重试", backoff)
        self._stopped.wait(backoff)
        backoff = min(backoff * 2, 30.0)
        try:
            if self.api:
                self.api.Release()
            self.start()                  # 重新创建 API 并 Init
        except Exception:
            logger.exception("CTP 交易重连失败")
```

**重连后必须遵守的顺序**（`OnRspUserLogin` 已自动执行）：
```
连接 → 认证 → 登录 → 结算确认 → 请求对账 → reconciled=true → 允许报单
```
**绝不允许**跳过对账直接恢复报单。

**重连期间的在途委托处理**：
- 断开瞬间处于 `SUBMITTED`/`PARTIAL` 的委托，重连后**必须靠对账确认状态**。
- 若对账发现该委托已不在柜台活动委托列表中（已成交/已撤），`reconcile()` 会把它标为 `UNKNOWN` 并抛异常（`live_trader.py:211-217`）——**这是正确行为**，需人工核对柜台后手工消解。

### 5.4 错单处理手册

| 错单类型 | 识别特征 | 处置动作 |
|---|---|---|
| **柜台拒绝** | `status: REJECTED`，`reject_reason` 有柜台错误信息 | 记录错误码 → 对照 1.5 节错误码表 → 修正参数 → 重新报（**拒绝是确定状态，可安全重报**） |
| **状态不确定** | `status: UNKNOWN`，`reject_reason: 发送结果不确定...` | **绝不重报**。查柜台该 `OrderRef` 真实状态 → 若存在则认领 → 若不存在则标记为已失效 → 触发对账 |
| **本地无、柜台有** | 对账时发现 | 严重！说明回报丢失。立即停止报单 → 从柜台拉全量委托/成交 → 补录本地 → 全量对账 |
| **柜台无、本地有（非终态）** | 对账时发现 | `reconcile()` 自动标 `UNKNOWN` → 人工确认柜台确实没有 → 手工标为失效 |
| **价格异常（天价/零价）** | 风控偏离检查拦截 | 检查上游价格来源；若是程序 bug 导致，**停止策略、修复后再开** |
| **重复报单** | 柜台 ErrorID 42 | 检查 `flow_path` 是否被多进程共用；检查 `OrderRef` 是否跨日重置正确 |
| **自成交** | 风控拦截 | 检查策略是否同时报买卖单；`risk_manager.py:84-91` 已拦截 |
| **平仓失败** | "无对应持仓" / "超过可用持仓手数" | 检查持仓方向映射；检查冻结量；**注意平今/平昨标志** |

**`UNKNOWN` 状态的标准处置流程（SOP）**：

```
1. 立即停止该策略新报单（不是停整个服务）
2. 用交易软件查询该 OrderRef / OrderSysID 的柜台真实状态
   ├─ 柜台存在且活动 → 认领，修正本地状态为该柜台状态
   ├─ 柜台存在且终态 → 修正本地状态为终态（FILLED/CANCELLED/REJECTED）
   └─ 柜台不存在     → 该报单实际未到达，标记为 CANCELLED 或 REJECTED
3. 修正 trading_state 中对应记录
4. 调用 request_reconcile()，确认 reconciled=true、is_ready=true
5. 记录到复盘日志：时间、原因、影响、处置耗时
6. 分析根因（网络？柜台？程序？），必要时降档
```

### 5.5 紧急停机开关（**当前缺失，必须新建**）

**现状缺口**：
- 实盘**没有**一键全平接口（`/api/v1/trade/close-all` 是模拟盘的，见 `routes.py:962`）
- 实盘只有单笔 `POST /api/v1/trade/live/order` 和单笔撤单
- 没有全局熔断开关

**必须新建三个开关（从软到硬）**：

#### 开关 1：软开关 —— 禁止新开仓（保留平仓能力）

```yaml
risk:
  live_enabled: false    # 置 false 后：拒绝所有开仓，允许平仓
```

**触发条件**：策略异常、指标异常、需要人工介入观察。
**特点**：改配置 + 重启服务（约 5 秒）；或做成可在页面切换的运行时开关（推荐）。

#### 开关 2：中开关 —— 撤销全部挂单 + 禁止报单

```python
# 新增 POST /api/v1/trade/live/cancel-all  (需 admin 角色 + X-Admin-Token)
@router.post("/trade/live/cancel-all")
def cancel_all_live_orders(...):
    """撤销当前全部活动委托。逐笔撤，失败的记入返回结果。"""
    orders = live_trader.get_orders(username)   # 或全量
    results = []
    for o in orders:
        if o["status"] in ("SUBMITTED", "PARTIAL"):
            r = live_trader.cancel_live_order(o["order_ref"], username)
            results.append({"order_ref": o["order_ref"], "result": r})
            time.sleep(0.2)      # 限速，避免触发柜台频控
    return {"cancelled": len(results), "details": results}
```

**⚠️ 必须限速**：连续快速撤单可能触发柜台流控或交易所异常交易认定。每笔间隔 ≥ 200ms。

#### 开关 3：硬开关 —— 一键全平（最危险，需二次确认）

```python
# 新增 POST /api/v1/trade/live/close-all
# 需 admin 角色 + X-Admin-Token + 请求体确认字符串
@router.post("/trade/live/close-all")
def close_all_live_positions(body: CloseAllRequest, ...):
    if body.confirm != "CONFIRM_CLOSE_ALL":
        return {"status": "REJECTED", "reason": "缺少确认字符串"}

    account, positions, active = live_trader._risk_state()
    # 1. 先撤全部挂单并等待生效
    # 2. 逐合约生成平仓单
    for key, pos in positions.items():
        if pos.volume - pos.frozen_volume <= 0:
            continue
        direction = SELL if pos.direction == "BUY" else BUY
        # ⚠️ 按 max_order_volume 拆单（平仓豁免单笔上限，但拆单更安全）
        remaining = pos.volume - pos.frozen_volume
        while remaining > 0:
            vol = min(remaining, batch_size)
            # 平今/平昨判定（SHFE/INE 必须区分）
            offset = decide_offset(pos, vol)
            req = OrderRequest(instrument=pos.instrument, direction=direction,
                               offset=offset, price=opponent_price(pos.instrument, direction),
                               volume=vol)
            live_trader.submit_live_order(req, username)
            remaining -= vol
            time.sleep(0.3)
```

**三种开关的执行顺序**：
```
发现异常 → 开关1（禁新开仓）→ 观察 30s
        → 若仍在恶化 → 开关2（撤全部挂单）→ 观察 30s
        → 若仍在恶化 → 开关3（一键全平）
```

**风险点**：
- **一键全平用对手价必然产生滑点**。急跌时平多单可能连续打穿多个价位。必须用市价对手价而非限价远价，否则平不掉。
- **平今/平昨错误会导致平仓被拒**。SHFE/INE 必须先查持仓快照的今仓数量。
- **限仓/最大手数**：单笔平仓即使豁免 `max_order_volume`，也建议拆单——单笔巨量单会直接打穿盘口。
- **必须限速**：每笔间隔 200–300ms，否则触发柜台流控。
- **全平后必须核对柜台持仓已归零**，不能只看接口返回。

### 6.1 回滚预案

#### 回滚决策树

```
发现异常
  ├─ 仅策略逻辑问题（连接/账务正常）
  │    └─ 回滚策略参数 → 保留交易通道
  ├─ 交易通道问题（连接/报单/回报异常）
  │    ├─ 有持仓 → 先平持仓（开关3）→ 再回滚通道
  │    └─ 无持仓 → 直接回滚通道
  ├─ 账务不一致（本地 vs 柜台）
  │    └─ 立即停止报单 → 全量对账 → 修正本地 → 再决定是否继续
  └─ 系统级故障（DB/Redis/进程）
       └─ 停服 → 恢复基础设施 → 全量对账 → 恢复
```

#### 三级回滚方案

| 级别 | 场景 | 动作 | 耗时目标 | 副作用 |
|---|---|---|---|---|
| **L1 参数回滚** | 阈值设置不当、策略参数问题 | 改 `settings.*.yaml` 的风险段 → 重启服务 | < 1 min | 服务中断 ~5s |
| **L2 通道回滚** | CTP 交易通道异常 | `live_enabled=false` → 重启 → 确认实盘接口全部拒绝 | < 2 min | 停止自动交易，人工接管 |
| **L3 完整回滚** | 严重故障/账务不一致 | 停服 → 平掉全部持仓 → 切回 `feed=sina` → 人工对账 | 视持仓而定 | 需人工全量核对 |

#### 回滚前置准备（**测试开始前必须完成**）

| # | 准备项 | 说明 |
|---|---|---|
| 1 | 生产配置快照 | `config/settings.prod.yaml` 已固定，回滚就是切回它 |
| 2 | 数据库备份 | 每日收盘后备份 `trading_state` 与新增的三张表 |
| 3 | 手工交易能力验证 | **确认能用交易软件人工平掉所有持仓**（万一程序全挂） |
| 4 | 回滚演练 | 在仿真环境完整演练一次 L3 回滚，记录实际耗时 |
| 5 | 联系人与通道 | 柜台运维电话、期货公司客服、交易所公告渠道 |
| 6 | 回滚脚本 | `stop.bat` 验证可用；准备 `rollback.bat`（切 profile + 重启） |

**⚠️ 最重要的一条：必须确认能用交易软件人工平仓。** 这是所有自动化失效后的最后防线。如果只有程序能下单，那么程序故障就等于资金失控。

#### 回滚演练脚本（仿真环境执行）

```
1. 记录当前状态（持仓、资金、活动委托）
2. 模拟故障：kill 服务进程
3. 执行 L3 回滚：用交易软件人工平掉全部持仓
4. 记录：平仓耗时、滑点、是否全部成功
5. 恢复：切回 simnow profile，启动服务
6. 验证：对账一致、is_ready=true
7. 复盘：记录演练耗时与暴露的问题
```

**建议每月演练一次**，直到能在 5 分钟内完成全平。

## 附录 B：与现有系统的对齐说明

本方案严格按现有代码能力设计，**不假设任何不存在的能力**。几处与常见做法不同、需特别注意的地方：

1. **交易柜只在 `feed=ctp` 时启动**。改 profile 时必须同时改 `feed`，否则下单接口会返回"柜台未连接"而看不出原因。

2. **实盘一键全平已落地**（原为缺失）。见模块五开关 3：`POST /api/v1/trade/live/close-all`，
   需 `confirm="CONFIRM_CLOSE_ALL"` + `X-Admin-Token` 双重确认。

3. **告警 Webhook 已接线**（原为死代码）。公共/私密双通道，交易类事件只走私密通道、永不进 WS 广播。

4. **风控阈值已全部外置**。模拟盘与实盘仍**共用同一个 `PreTradeRiskManager` 类**，
   但模拟盘已在构造时显式豁免实盘专属开关。⚠️ **改该类默认值时必须回归模拟盘测试**，
   本次改造就曾因此导致模拟盘开仓被全量拦死（25 失败 + 20 错误）。

5. **对账新鲜度只能靠进程内 `monotonic`**。`trading_state` 表没有 `updated_at` 字段，无法从库里判断对账是否新鲜。
   （`/trade/live/status` 已暴露 `sync_age_seconds` 供观测。）

6. **`UNKNOWN` 会导致系统"看起来卡死"**。`reconcile()` 抛异常 → `reconciled=false` → 所有报单被拒。这是正确设计，但需要 SOP（见 5.4）配合，否则现场会误判为故障而去改代码绕过——这是最危险的处置方式。

7. **`max_order_volume` 只卡开仓不卡平仓**是有意设计（历史故障：裸空 177 手被 50 手上限卡死，连续 4 次平仓全被拒）。改造风控时**必须保留这个豁免**，任何"顺手统一一下"的改动都会重现该故障。
   现在 `scripts/live_preflight.py` 的 E9 项会自动回归验证这一豁免。

8. **告警隐私保护必须保留**。交易类事件只写库、不广播 WS。实盘告警需走独立私密通道。
